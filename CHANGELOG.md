# Changelog

All notable changes to Outpost. The format follows Keep a Changelog; versions follow SemVer.

## Unreleased

### Added
- The `outpost.ssh` package logs every ssh and scp call at DEBUG on its own logger: the command's first line, how it ended, the time taken, and for `write`, `put` and `get` the file's owner and permissions in words (`owner root may read, write; group root may read; others may read (0644)`).
- `ssh.SshError` with two subclasses: `Unreachable` (ssh could not log in, or the connection broke) and `CommandFailed` (the command ran and failed; its `Result` is in `.result`). A marker line before and after each command tells the two apart, so a command that exits 255 is no longer taken for ssh failing.
- Developer tools: `scripts/format.sh` (ruff format and import sort; `--check` changes nothing), ruff lint rules E, F, W, I, B, UP, SIM, N and C901, pyright in basic mode over `outpost/`, a `.pre-commit-config.yaml` (`pip install pre-commit && pre-commit install`), and CI jobs for the format, the lint and the types. ruff and pyright are in the `dev` extra.
- The rules for the code: `CLAUDE.md`, `docs/development/style.md` (the `outpost/ssh` package is the model), `docs/glossary.md` (one word per idea) and `docs/architecture/target.md` (the map of the cleanup, and what each step built).

- Two OS package kinds next to `apt`: `apk` for Alpine (`apk: {branch: v3.20, packages: [...]}`) and `rpm` for the RHEL family (`rpm: {distro: rocky9 | alma9 | fedora40 | stream9, packages: [...]}`). Both resolve the full dependency tree inside a container of the real distro (`apk fetch --recursive`, `dnf download --resolve --alldeps`), land in `box/apk/<branch>/` and `box/rpm/<distro>/`, and are uploaded to Gitea's Alpine registry (one branch each, repository `main`) and RPM registry (one group per distro). `mirrors.yml` gained `alpine`, `rocky`, `alma`, `fedora` and `centos_stream`.
- The config image and the nodes now configure apk and dnf as well as apt: `/etc/apk/repositories` and Gitea's RSA key under `/etc/apk/keys/<owner>@<fingerprint>.rsa.pub` (the name Gitea signs with, taken from the key endpoint's `Content-Disposition`), `/etc/yum.repos.d/outpost.repo` with `gpgkey` and `sslcacert`, and `/etc/outpost/gitea-rpm.asc`; the stock `*.repo` files of Rocky, Alma, Fedora and CentOS Stream are overwritten with a comment in the config image, and `/etc/apk/repositories` is blanked when Gitea has no Alpine branch. `state/upload.json` records `apk_branches` and `rpm_distros` next to `distros`.
- `infra setup` reads `ID` and `ID_LIKE` from `/etc/os-release` and configures the matching client on each node (apt, apk or dnf), parking the stock sources the same way for all three; `infra upgrade` runs `apt-get`, `apk` or `dnf` by family; `hosts` records `id_like` and `version_id`.
- The verification checks `apt sources are gitea only` and `apt update works offline` are now `package sources are gitea only` and `package index updates offline`, one script that picks apt, apk or dnf on the node.
- A third shipped smoke check, `hello-alpine`: an Alpine image built with `COPY --from=config / /` and `apk add --no-cache curl` from Gitea, run, then a container that must fail to reach pypi.org. `needs/demo.yml` lists `apk: {branch: v3.20, packages: [curl]}` for it.
- The dashboard's project scan reads `apk add` and `dnf`/`yum`/`microdnf install` lines and proposes `apk` and `rpm` blocks, with the branch or distro read from the base image (`alpine:3.20` and `python:3.12-alpine3.20` are `v3.20`, `rockylinux:9` is `rocky9`, `fedora:40` is `fedora40`).
- Named exceptions to the seal: an optional `egress_proxy` section in `servers.yml` (`allow:` host names or `*.domain` wildcards; optional `host`, default the Gitea host, `port`, default 3128, `distro`, `name`). `outpost proxy setup` installs tinyproxy from the distro's package through Gitea (apt on Debian and Ubuntu, dnf on the RHEL family; Alpine is refused) on the proxy host, writes `/etc/tinyproxy/tinyproxy.conf` and the anchored allow list `/usr/share/tinyproxy/outpost.allow` (`FilterDefaultDeny Yes`), runs it as `outpost-proxy.service` under the system user `outpost-proxy`, logs every request and refusal to `/var/log/tinyproxy/tinyproxy.log`, and seals the host with one exception: that user may open TCP 443 and 80, through an owner match in a new `OUTPOST-OUT` chain hooked from `OUTPUT` in the filter and security tables. Every other host's egress script is unchanged. `outpost proxy verify` checks the service, the package source, the allow list, the exception, an allowed name and a refused one; `state/proxy.json` records it. See docs/architecture/proxy.md.
- `outpost needs` and `fetch` add `tinyproxy` to the apt or rpm needs of the proxy host's distro (from `egress_proxy.distro` or the cached `outpost hosts` facts).
- Nodes get the proxy variables (`HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY`, both cases, and `OUTPOST_PROXY_ALLOWED`) in `/etc/outpost/proxy.env`, `/etc/profile.d/outpost.sh`, `/etc/environment` and, on Docker nodes, `proxies.default` of root's and the runner's `~/.docker/config.json` (nothing on the Docker daemon); k3s gets a ConfigMap `outpost-proxy` in `default`. A proxy on another host also joins every node's allow list and `/etc/hosts`. `infra verify` checks the proxy from each node. The config image carries `proxy.env` and the profile exports. Without a proxy, `/etc/outpost/proxy.env` is a comment so `env_file:` can always name it.
- Smoke checks can say `requires: [proxy]` and are skipped without one; new `hello-proxy` (Compose, Swarm) and `hello-proxy-k3s` checks; check steps get `PROXY_URL`, `PROXY_ALLOWED` and `PROXY_REFUSED`.
- The demo reads the proxy variables (`env_file` in compose.yml and stack.yml, an optional `envFrom` in k8s.yml), shows a "through the proxy" card, and `/healthz` reports `proxy_ok` (null without a proxy). The build-time probe still tests the direct path only.
- `outpost hosts` records the tinyproxy version, `outpost-proxy`'s state and the last 20 lines of the proxy log; the proof report has a *Named exceptions* section; the dashboard has an egress proxy card on the Servers page, the proxy role on Machines, and Set up / Verify buttons on Keep it healthy.

### Changed
- Breaking for library users: `Host.run(script, check=True)` is `Host.run(script, raise_on_failure=False)`. A failing script comes back as a `Result` unless `raise_on_failure=True`; every caller in Outpost that relied on the old raise asks for it. There is no alias for `check`.
- The code is laid out by idea, one file per idea, each package with an overview, an example and a map of its files in `__init__.py`: `outpost/ssh.py` is the package `outpost/ssh/`; `cli.py` is `outpost/cli/`, one module per command; `oci.py`, `config.py`, `demo.py`, `hosts.py`, `report.py` and `infra/proxy.py` are packages; `infra/common.py` is `infra/node/`, in named steps; `egress.py`, `hostsfile.py` and `client_config/` sit below `gitea/` and `infra/`, so Gitea no longer imports infra; the dashboard is split into route tables, `overview`, `files`, `servers_form`, `reach`, `runs`, `status/` and `projects/`. No function is left marked too complex.
- The folder `outpost init` makes is the **workspace** (class `Workspace` in `outpost/workspace.py`, was `Platform` in `outpost/paths.py`; `templates/platform` is `templates/workspace`). Commands get one `AirGappedSystem` (`outpost/system.py`) that holds the workspace, its config (`outpost/config/`: `servers.yml`, `mirrors.yml`), its state and its secrets, and makes the `Host` for a server; `outpost/endpoints.py` says how nodes reach Gitea and the egress proxy.
- The help, the messages, the report's heading ("What this workspace is") and the dashboard say "workspace" instead of "platform".
- The whole repository is formatted with ruff (line length 120).
- No process-wide globals for the CPU type or the ssh config file: `versions.ARCH`, `versions.use_arch` and `ssh.use_config` are gone. `AirGappedSystem` holds `arch` and `ssh_config` (chosen by `ssh.choose_config_file` from `ssh_config:` in `servers.yml` or `OUTPOST_SSH_CONFIG`, with the same rules), `Host` and `Tunnel` take a `config_file`, and the arch is passed to every function that needs it. Commands, flags and `OUTPOST_SSH_CONFIG` are unchanged.

- The verification check `public internet rejected` runs `curl --noproxy '*'`, so it tests the direct path even where a session carries proxy variables.
- Container images now live under the one Gitea organisation like every other kind of package, with their original path nested below it: `python:3.12-slim` is uploaded to `<gitea>/pkgs/library/python:3.12-slim`, `bitnami/redis:7` to `<gitea>/pkgs/bitnami/redis:7`, `ghcr.io/org/app:1.4` to `<gitea>/pkgs/org/app:1.4`. No organisation per image owner is created any more.
- Dockerfiles, Compose, stack and Kubernetes files reference the Gitea copy explicitly (`FROM ${GITEA}/${ORG}/library/python:3.12-slim`). Nothing on a node rewrites image names: `daemon.json` no longer sets `registry-mirrors` and k3s's `registries.yaml` no longer mirrors `docker.io`. A bare Docker Hub name on a sealed node fails at once, like any other reach for the internet. The verification check `docker uses gitea mirror` is replaced by `docker trusts and reaches gitea registry`.
- The demo and the `hello-python` and `hello-k3s` checks use the explicit names; the dashboard's project scan reads a Gitea name back into the need that produces it (`${GITEA}/${ORG}/library/python:3.12-slim` is proposed as `python:3.12-slim`; a literal `gitea.internal/pkgs/...` name is read back when `servers.yml` names that Gitea).
- Migration: re-run `outpost upload` so images land under `pkgs`, re-run `outpost infra setup <name>` so `daemon.json` and `registries.yaml` are rewritten, and change the `FROM` and `image:` lines of your projects to the Gitea names (`outpost init` templates and `demo/` are updated; an existing `demo/` folder is yours to edit).

### Fixed
- `outpost gitea backup` writes to `backups/` in the workspace wherever outpost runs; it used the current directory.
- `outpost upload` prints a warning when it cannot check the box's signature (no `manifest.sig`, or `pki/box.pub` missing), instead of skipping the check without a word.
- `outpost fetch`: one image or file that fails no longer stops the rest of its kind; it is listed at the end and the exit code is still 1.
- HTTP PUT and POST are no longer retried after a server error, since the request may have landed; GET and HEAD still are.
- Image layers and generic, Debian, Alpine and RPM package uploads stream from disk instead of reading the whole file into memory.
- Gitea's certificate is reissued when `gitea.name` or `gitea.ip` changes; the check was a substring match on the name and ignored the IP.
- `fetch` after `pack` left a stale `manifest.sig`, which made `upload` refuse the box. A new manifest now drops the old signature.
- An unquoted `python: 3.10` in a needs file is a clear error that says to quote it (YAML reads it as 3.1).
- `upload` no longer counts images Gitea already had as uploaded, and sends no manifest PUT when the tag already names it.
- `gitea backup` always records the archive's sha256, hashed in chunks; it read the whole archive into memory and skipped the hash above 2 GB.
- `infra verify` (`package sources are gitea only`, `package index updates offline`), the proxy's `tinyproxy installed from gitea` and `infra upgrade` failed on Debian and Alpine with `ID_LIKE: unbound variable`.
- A k3s `args:` with a quote, `$` or a backtick was mis-quoted (Python's `repr` was used as shell quoting).
- `egress seal|open --reason` with a `'` in it failed, and shell syntax in it ran on the server. The reason is now one quoted argument.
- The `coredns at pinned version` verification failed now and then: `coredns -version | grep -q` let coredns die of SIGPIPE under `pipefail`. Version and source verifications now read the whole output.
- `outpost lab up` also forgets the old servers' cached facts in `state/hosts/`, so the dashboard and the report no longer show removed servers as sealed.
- A broken `mirrors.yml` no longer blanks the whole dashboard; the error is shown.
- One needs image reference that does not parse no longer flags every image in the box as unneeded.
- `outpost hosts` works on servers without `PRETTY_NAME` in `/etc/os-release`, or without the file at all.
- `outpost report` no longer fails when the ssh config file named in `servers.yml` is missing.
- `Host.ip()` on a server without `hostname -I` read a fixed word of `ip route get`, which is wrong when the default route has no gateway (`1.0.0.0 dev eth0 src ...`); it now takes the word after `src`.
- The ssh config file is chosen once, when `servers.yml` is read, and that fails at once on a missing file, or when `ssh_config:` in `servers.yml` and `OUTPOST_SSH_CONFIG` name two different files, instead of every ssh call failing later with exit 255 as if the server were down. The dashboard shows such a file as a message.

- `outpost upload` failed at the first image with `NAME_INVALID`: the first version of the one-organisation layout joined owner and image as `library--python`, which the OCI spec allows but Gitea's own name rule (one `.`, `_` or `-` between alphanumerics) rejects. Images now use the nested path `pkgs/library/python`, checked against a real Gitea in the integration suite.
- `apk add` over https in a build failed with `certificate verify failed`: apk has no CA option and reads only OpenSSL's defaults, and an Alpine base has no `update-ca-certificates`. The config image now also carries the CA as `/etc/ssl/certs/<subject hash>.0`, where OpenSSL looks it up (`hello-alpine` on the lab).
- The full-flow integration test asked for the old check name `apt sources are gitea only`.
- Since 0.1.0 `/etc/apt/sources.list.d/outpost.list` was empty on every apt node and on the Gitea host: setup probed each suite with `curl -I` (HEAD), and Gitea routes the Debian registry's `dists/` files for GET only (405 for HEAD; its Alpine and RPM registries answer both). The probe is now a GET. Re-run `outpost infra setup` on Debian and Ubuntu nodes to get the sources written.
- `package sources are gitea only` passed on that empty list, because it only looked for sources pointing elsewhere. It now also needs at least one apt source, apk repository or rpm repository pointing at Gitea, and says which file is empty when there is none. `package index updates offline` took the exit status of `tail`, so it passed even when `apt-get update`, `apk update` or `dnf makecache` failed; it now takes the tool's own, and the apt branch of the sources check took only the last of its two foreign-source tests into account.
- On the Gitea host the egress proxy's URL is now `http://<gitea address>:<port>` instead of the Gitea name. With the name, apt sent a `CONNECT` for every `https://<gitea name>` fetch to Gitea itself (its `no_proxy` handling keeps the proxy's host name, and the two were equal), so `apt-get update` in a Docker build on a node with the proxy variables failed with "Reading from proxy failed". Re-run `outpost proxy setup` to rewrite the variables on the nodes, and `outpost upload` for the config image.
- The egress proxy did not start on hosts whose kernel confines `/usr/bin/tinyproxy` with an AppArmor profile named `tinyproxy` (Ubuntu 26.04 loads one, and the GitHub runner's kernel applied it inside the lab's privileged containers): the profile lets tinyproxy read `/etc/tinyproxy/tinyproxy.conf` and `/usr/share/tinyproxy/*` and write `/var/log/tinyproxy/tinyproxy.log`, nothing else, so `/etc/outpost/proxy.conf` was "Could not open config file" even for root. The configuration is now `/etc/tinyproxy/tinyproxy.conf`, the allow list `/usr/share/tinyproxy/outpost.allow`, the log `/var/log/tinyproxy/tinyproxy.log` (rotated by `/etc/logrotate.d/tinyproxy`, which replaces the package's), and the unit hands the log directory to `outpost-proxy` before every start; no AppArmor rule is added and the same paths work without a profile. `proxy setup` removes the files of an earlier setup. When the proxy does not start, setup reports `namei -l` of each file, tinyproxy run by hand as the user and as root, AppArmor's state and the kernel's denials.

### Security
- The Gitea API token is no longer on a `curl` command line on the Gitea server, where `ps` shows it to every user: it goes on stdin.
- The Gitea admin password is no longer on `gitea admin user create --password` during the first setup: Gitea makes a random one (`--random-password`), and a password already in `secrets/gitea-admin-password` is set back through the admin API by a `curl` that reads its request on stdin.
- The runner's registration token is no longer on `gitea-runner register`'s command line; it is passed in `GITEA_RUNNER_REGISTRATION_TOKEN`.
- The dashboard refuses requests from other web pages: a non-GET request with a foreign `Origin`, a POST or JSON PUT without `Content-Type: application/json`, and any request whose `Host` is not 127.0.0.1 or localhost (which also blocks DNS rebinding) get 403.
- `backups/`, which holds Gitea's keys, secrets and database, was removed from the repository's history and is in `.gitignore`.

### Documented
- Gitea Actions jobs run as root on the first node of each infrastructure (host mode), so whoever can push a workflow can open that node's seal. A runner user would still need Docker or the k3s admin config, which are root-equivalent; it is a known limit in `docs/reference/limits.md`.
- The docs speak the glossary (`docs/reference/platform-folder.md` is `docs/reference/workspace.md`), and the module map, the counts, the ssh config rules and the commands match the code.

## 0.1.0 - 2026-10-26

First public release.

### What it does
- `fetch` downloads what lockfiles, Dockerfiles and needs files ask for (PyPI wheels, npm tarballs, apt packages with their dependency trees, container images, plain files) into one folder, the box, plus the pinned Gitea, Docker, Compose, buildx, CoreDNS, k3s and Actions runner binaries.
- `gitea setup` installs a single-binary Gitea over SSH with a private CA, an admin, a narrowly scoped token and an organisation, then seals the server.
- `upload` pushes the box into Gitea's PyPI, npm, Debian, generic and container registries and builds the `config` image.
- `infra setup` prepares Compose, Swarm or k3s nodes: trust, client configuration, seal, then CoreDNS, Docker or k3s and the Actions runner installed from Gitea; `infra verify` proves it with a table of checks.
- `check` runs smoke scenarios; `demo push` deploys a real application through Gitea Actions on the sealed nodes, with a build-time and a live internet probe.
- The seal is an iptables chain built in the filter table (REJECT) and the security table (DROP), hooked into OUTPUT, FORWARD and DOCKER-USER, restored at boot, so hosts, containers and pods are all covered.
- `lab up` gives four throwaway servers in Docker to run the whole thing without a VPS.
- Day two: `hosts` (what every server runs), `gitea backup` and `gitea restore`, automatic backup before a Gitea upgrade, `infra upgrade` (OS security updates from Gitea), `pki rotate`, `report` (one HTML page of evidence).
- `outpost ui`: a local dashboard for people who do not want to type commands: a Home page with three questions, a Machines page, Applications, step-by-step pages that say what each button will do, narrated progress, failures translated into a sentence and a fix, a history in plain words, and the proof report.
- Architectures: `arch: amd64` (default) or `arm64` in `servers.yml` selects every download.

### Known limits
See docs/reference/limits.md. Tested on Ubuntu 24.04 containers in the lab; no run on real virtual machines yet.
