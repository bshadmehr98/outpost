# Decisions, and what we learned

A record of the choices behind Outpost and the things that did not work on the first try.
Read it as the "why" behind the architecture pages and as a list of traps for anyone building
something similar.

## Decisions

**One Gitea instead of five services.** The scripts this grew out of ran Gitea next to aptly and nginx, and
the natural next steps were a PyPI proxy, a registry and a CI server. Each is fine; together
they are a project of their own. Gitea's package registries speak the native protocols well enough that
`pip`, `npm`, `apt`, `docker` and `curl` cannot tell the difference, and it brings git and CI.
The price: Gitea's Debian registry re-signs indexes with its own key, which nodes must fetch,
and the container registry is simple (no garbage collection UI). Worth it.

**The laptop is the control machine; servers get SSH and nothing else.** No agent, no
Python on the servers, no inbound ports to Outpost. Every change is a shell script you can
read in the source. The Gitea API is reached through an SSH tunnel for the same reason.

**Standard library plus PyYAML.** Outpost itself must install anywhere, including on a
locked-down laptop. HTTP is `urllib`, TLS is `ssl`, certificates are the `openssl` CLI,
image pulls are a 260-line OCI client. Adding a dependency is a decision, not a convenience.

**Files are the state.** The platform folder is the database. The dashboard reads it and runs
the CLI; it can never do something the CLI cannot. This made the dashboard a viewer plus a
button panel, which is all it needs to be.

**Lockfiles are the input.** Projects already pin their dependencies; Outpost reads
`uv.lock`, `poetry.lock`, `package-lock.json` and friends instead of maintaining a second list.
Loose specs (`httpx`, `chalk@5.3.0`) exist for quick experiments and are documented as such.

**Seal with REJECT in the kernel, not with client configuration.** Pointing pip at Gitea is
not a guarantee; a `--index-url` flag undoes it. An iptables rule below every client is. REJECT
rather than DROP so failures are immediate and name the host, which turns the firewall into a
to-do list generator.

**Seal before installing the runtime.** Docker, k3s, CoreDNS and the runner are downloaded
from Gitea *after* the node is sealed. The setup succeeding is then itself the proof that the
box was complete.

**A config image for builds.** Host configuration does not reach into `docker build`. One
image with the client files, copied in with `COPY --from=config / /`, keeps Dockerfiles to a
one-line change and makes the container see exactly what the host sees, because both are
generated by the same function.

**CoreDNS on every node.** pip refuses HTTPS to a bare IP, containers cannot see
`/etc/hosts`, and we did not want a DNS server as a dependency of the platform. One static binary
per node with a six-line config answers the one name that matters and forwards the rest.

**Runners in host mode.** The default Docker mode needs a job image, vendored actions and
Docker-in-Docker, all of which would have to be mirrored and would make the pipeline a
special case. Host mode makes a job a shell script on a sealed node, which is exactly what a
person would type.

**The lab is the test rig.** `outpost lab up` and the integration suite share one
implementation: Ubuntu containers running systemd and sshd, driven over SSH like real
servers. Whatever passes in CI is what a user sees, and the tutorial can be followed with no
servers at all.

## What we learned

**k3s pods could reach the internet while the host could not.** The first seal hooked only
`OUTPUT` (host traffic) and `DOCKER-USER` (Docker's hook). Pod traffic is *routed*: it passes
`FORWARD`, where flannel accepts it. Found by the demo page's live probe, not by any host-level
check. Fix one: hook `FORWARD` too. Lesson: every runtime needs an in-container egress test.

**Being first in `FORWARD` cannot be promised.** With the `FORWARD` hook, a fresh node still
leaked: k3s starts after the seal, and kube-router, kube-proxy and flannel each insert at the
top of the chain, kube-router with a rule that accepts all policy-compliant pod traffic. The
lab had passed only because it was re-sealed with k3s already running. Fix two: build the chain
again in the `security` table, which the kernel evaluates after `filter` and which nothing
else writes to. `REJECT` is not allowed there, so the backstop drops. Lesson: never rely on
rule order in a chain other software edits; use a hook it does not use.

**A 1-second readiness probe against a health check that measures the internet.** Once pods'
packets were dropped instead of rejected, `/healthz` took two seconds (the probe's timeout) and
Kubernetes marked the pods unready forever. Fix: `timeoutSeconds: 5`. Lesson: when you change
*how* something fails, check who was timing the failure.

**Gitea's automatic job token cannot push packages.** `docker login` with `GITEA_TOKEN` fails
with "unauthorized". A token with `write:package` has to be created with the password and
stored as a repository secret.

**Tokens outlive servers.** Recreating the lab, or reinstalling Gitea, left a stored token the
new server did not know, and every API call failed with 401. Fix: check the token on use and
replace it. Lesson: anything stored about a server should be verifiable against the server.

**Probing many addresses is slow.** The first internet probe connected to every address a
name resolved to, which took 10 to 17 seconds per page on a sealed node. One address, two
seconds, in parallel: the page now loads in about two seconds.

**`.format()` and workflow files do not mix.** `${{ secrets.X }}` is a format string's worst
enemy; the workflow generator uses plain `str.replace` on placeholders.

**pip wants wheels for the target, not the host.** `pip download --only-binary=:all:
--python-version 3.12 --platform manylinux2014_x86_64 ...` resolves for the server even on a
Mac. Packages without wheels fall back to an sdist, fetched without dependencies.

**Debian packages must be resolved by Debian.** No host-side tool reproduces apt's resolver
reliably; running the real one in a throwaway container of the right distro is simpler and
exact. Download the full tree, because a slim image lacks what a full image has.

**Docker's registry mirror only applies to Docker Hub names.** `FROM ghcr.io/x/y` is not
mirrored and must be written with the Gitea name. Images keep their owner on upload for the
mirror to work at all (`library/python`).

**A token with `--scopes all` is a root password.** The first version kept an all-scope admin
token in `secrets/gitea-token` because it was convenient. It could create users and change the
admin password. Now the token has `write:organization, write:repository, write:package,
read:user, read:misc`, which covers uploads, the demo repository and runner registration, and
the runners belong to the organisation instead of the instance, which is what made the admin
scope unnecessary. The integration suite checks that the token gets a 403 from the admin API.

**`systemctl enable --now` does not restart a running daemon.** The Docker install used it, so
bumping the pinned Docker replaced the binaries on disk while the old daemon kept running, and
`verify` was happy because `docker --version` is the client. Fixed with an explicit restart and
a `docker info` version check in `verify`. Lesson: verify the server side of everything, not the
client.

**Back up by stopping Gitea, not by `gitea dump`.** `gitea dump` writes the database as SQL and
restoring it needs the `sqlite3` CLI on the server, which a minimal host does not have. Stopping
Gitea for the ten seconds a `tar` of `/var/lib/gitea/data` and `/etc/gitea` takes gives an
archive that is restored with `tar` alone. The pause is announced and short; the simplicity is
worth it. An upgrade takes the backup by itself first.

**Progress is a convention, not a protocol.** The dashboard's narrated progress is nothing
more than log lines that start with `==> `, optionally with `[i/n]`. The CLI prints them for
humans anyway; the page turns them into a step list. No events, no JSON, no second channel.

**Facts about machines are cached as files.** `state/hosts/<alias>.json` is written by every
command that touches a host and by `outpost hosts --refresh`. The Machines page and the report
read the files, so they are instant and work offline, and the only SSH the dashboard does by
itself is the optional five-minute heartbeat. Files are the state, again.

**Translate errors, do not hide them.** A table of twenty regexes maps the failures people hit
in the first week to a sentence and a fix. The full output stays one click away. Nothing is
swallowed; the first known cause is just put into words first.

**One architecture per platform folder.** `arch:` in `servers.yml` changes every download
name, the pip platform tags, the apt container platform and the image manifest selection, and
setup refuses a server whose `uname -m` disagrees. A mixed fleet is two folders. Supporting
both in one box would double its size for everyone.

**/etc/hosts is not yours.** The reboot test (a container restart with systemd starting from
scratch) came back sealed, with CoreDNS, Docker and k3s up, and the node unable to resolve the
Gitea name: Docker had regenerated `/etc/hosts`. cloud-init does the same on most cloud images
at every boot (`manage_etc_hosts`). The line is now written by a oneshot unit, `outpost-hosts`,
that runs after cloud-init and before CoreDNS, Docker, k3s and Gitea, and `verify` checks that
the unit is enabled. Lesson: anything a node must have at boot needs a unit, not a one-time edit,
and the reboot test belongs in the suite.
